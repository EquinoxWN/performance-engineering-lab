## Analyze

- **Cache lines: same O(n), 12x to 25x apart.** Gathering 16,777,216 ints through a random
  permutation took 16.2 ns/element in Java and 17.6 in Node.js against 0.66 and 0.96 sequentially;
  CPython took 417 vs 33.7 ns/element. With 16 KB of data the order made no difference (ratios
  0.91 to 1.09). The predictions (at least 4x and 1.5x) were right in direction but far too
  cautious. 16 to 18 ns per random load is well below a full DRAM round trip, which is consistent with
  the CPU overlapping several independent misses; hardware counters (M2) are needed to confirm it.
  CPython's list stores pointers to separate int objects, so each random element touches two
  unrelated cache lines (the list slot and the object); the index list's own objects were
  re-allocated in reading order so they do not add a third.
- **Branch prediction in Java: the classic effect is real on this JDK.** C2 compiled the `if` as a
  branch: 5.23 vs 0.471 ns/element on random vs sorted bytes (11.1x), while the masked version is
  flat (0.59 vs 0.62). The branchless kernel is slower than the branchy one on sorted data (0.59 vs
  0.47): with a perfectly predicted branch, the mask's extra arithmetic costs more than it saves.
- **Branch prediction in CPython: small, and "branchless" is a pessimization.** Random order costs
  1.28x (24.8 to 31.9 ns), but the masked kernel (43.1 to 46.1 ns) is slower than the branchy
  kernel even on random data: in the interpreter each extra operation (`>>`, unary `-`, `&`) costs
  more than a misprediction.
- **Boxing in Java: 10x for the list, 25x and 24 B/element for the boxed accumulator.**
  `ArrayList<Integer>` costs 1.52 vs 0.146 ns/element; the `int[]` loop at 0.146 ns/element (about
  7 elements per ns) is consistent with a vectorized sum (not checked against the generated
  assembly). `Long s += v` allocated exactly 24.0 B/element in every fork: escape analysis did not
  remove it. The prediction said 16 bytes because it assumed an `Integer`-sized object; a `Long`
  is a 12-byte header plus an 8-byte value, padded to 24 bytes.
- **H18 refuted (CPython `array('q')` is 1.26x slower than `list`).** Root cause, checked with
  `dis.get_instructions(..., adaptive=True)` and identity tests: reading from an `array('q')`
  creates a new int object for every element (`a[0] is a[0]` is `False` for values above 256), and
  the loop over an array stays on the generic `FOR_ITER`, while a list hands out existing references
  through the specialized `FOR_ITER_LIST`. Unboxed storage saves memory, not time, when every element
  is boxed again on the way out.
- **H19 refuted (`__slots__` objects only 1.11x slower than ints).** The adaptive interpreter
  specializes the attribute load to `LOAD_ATTR_SLOT` (checked with `dis`), a direct offset read, so
  the extra cost per element is about 3 ns, not the 50% predicted.
- **H09 and H16 refuted (Node.js): a measurement-system defect, not a hardware result.** With
  default flags the typed-array kernels ran far slower than expected: `Int32Array` sum 2.83
  ns/element (slower than an array of objects, 2.46), branchy on sorted bytes 4.44 ns/element (Java:
  0.47). A pinned probe showed the same branchy kernel at 0.77 to 4.21 ns/element depending only on
  how the calling code was written (closure or direct call, result accumulated or passed to
  `do_not_optimize`), and at 0.64 to 0.79 ns/element in all those forms with `--no-maglev`. The
  likely root cause is that, under Node.js 24's default tiering, the measured function sometimes
  keeps running mid-tier (Maglev) code instead of TurboFan code. This is inferred from the flag's
  effect, not proven with `--trace-opt` output; M2 confirms it with V8's tracing and profiles.
- **Defects found while building, and their root causes:**
  - The Java test helper read every JSON integer as a `double`: `cond ? Double.valueOf(t) :
    Long.valueOf(t)` unboxes both branches and promotes the `Long`, a boxing trap of exactly the
    kind this project measures. Replaced with an `if`.
  - JMH's annotation processor also ran on the test sources and its "no processor claimed" warning
    failed `-Werror`; test compilation now runs with `-proc:none`.
  - One verdict-rule mutant (`<` vs `<=` at the boundary) survived the first test suite; a boundary
    test was added.

## Control

- **The spec loader refuses to measure without a hypothesis:** any (runtime, experiment, size) cell
  without one fails `load_spec`, so the runner and every test fail.
- **Harnesses refuse wrong work:** JMH `@Setup` throws, pyperf workers raise and `bench.js` exits 3
  when a kernel's result differs from the expected sum, before any timing.
- **Shared checksums** in the Java, Python and JavaScript suites keep the inputs identical across
  runtimes; `BenchStateTest` keeps the JMH `@Param` defaults equal to the spec.
- **The report exits 3** when any hypothesis lacks results or a result has no spec cell, and judges
  nothing from fewer than 3 forks.
- **CI** (`.github/workflows/ci.yml`): lint, tests, a smoke run of every cell through JMH, pyperf and
  mitata with its `RESULT` line as a `::notice` (or `::error`), and the dependency audit.
- **Containment** is tested: every JMH command caps both heaps and points temp, crash and dump files
  into `.tmp/`; result readers refuse oversized or malformed input.
